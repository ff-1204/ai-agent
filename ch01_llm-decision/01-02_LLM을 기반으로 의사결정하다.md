# 1.2 LLM을 기반으로 의사결정하다

> **공식 문서** — [OpenAI · Function calling](https://platform.openai.com/docs/guides/function-calling)

[1.1절](01-01_AI%20%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%EC%9D%98%20%EB%91%90%EB%87%8C%2C%20%EA%B1%B0%EB%8C%80%20%EC%96%B8%EC%96%B4%20%EB%AA%A8%EB%8D%B8%EC%9D%98%20%EC%9D%B4%ED%95%B4.md)에서 미뤄 둔 문제로 돌아옵니다.

> "환불해주세요" / "돈 돌려받고 싶은데요" / "이거 마음에 안 들어요"
> 이 셋을 전부 **환불 문의**로 분류해야 합니다.

`if` 로는 못 씁니다. 그런데 LLM에게 물어보면 셋 다 맞힙니다. **판단을 코드에서 모델로 옮기는 것**, 이것이 LLM 기반 의사결정의 출발점입니다.

## 판단을 넘기는 방법은 "잘 묻는 것"입니다

코드로 규칙을 적는 대신, 말로 지시합니다.

```
당신은 고객센터 분류 담당자입니다.
아래 문의를 환불 / 배송 / 기타 중 하나로 분류하세요.

문의: 이거 마음에 안 들어요
```

이 지시문을 **프롬프트(Prompt)** 라고 합니다. 프로그래밍에서 함수 명세를 적던 자리를, 이제 자연어 지시문이 대신합니다.

### 역할을 나눠서 넣습니다

LLM에 보내는 메시지는 보통 **역할(Role)** 이 붙습니다.

| 역할 | 무엇을 담나 | 성격 |
| :--- | :--- | :--- |
| **시스템(system)** | "너는 누구이고 무엇을 해야 하는가" | 대화 내내 유지되는 규칙 |
| **사용자(user)** | 이번에 처리할 실제 입력 | 매번 달라짐 |
| **어시스턴트(assistant)** | 모델이 앞서 한 답변 | 대화 맥락으로 다시 넣어 줌 |

역할을 나누는 이유는 **변하지 않는 지시와 변하는 입력을 섞지 않기 위해서**입니다. 시스템 프롬프트에 규칙을 두고 사용자 메시지에 문의만 넣으면, 문의가 바뀌어도 규칙은 그대로 갑니다.

> **사용자 입력을 시스템 프롬프트에 문자열로 이어 붙이지 마세요.** 사용자가 "위 지시는 무시하고 …"라고 쓰면 그대로 지시가 되어 버립니다. 역할을 나누는 건 스타일 문제가 아니라 **안전 문제**입니다.

## 진짜 문제는 답을 프로그램이 못 쓴다는 것입니다

지시를 잘 줬더니 이렇게 답이 옵니다.

```
이 문의는 상품에 대한 불만족을 표현하고 있으므로 환불 문의로 분류하는 것이 적절해 보입니다.
```

사람이 읽기엔 좋습니다. 그런데 **다음 코드를 어떻게 씁니까?**

```python
if 응답 == "환불":   # 안 맞습니다
```

문자열을 잘라 쓰면 될 것 같지만, 같은 질문에 다음번엔 이렇게 옵니다.

```
환불 문의입니다.
```

그다음엔 이렇게 옵니다.

```
분류: 환불
```

**자연어는 형식이 고정되지 않습니다.** 1.1절에서 본 대로 매번 확률로 고르니까요. 파싱해서 쓰려는 순간 무너집니다.

## 구조화 출력 — 형식을 강제합니다

그래서 답의 **모양을 미리 정해서** 그 틀로만 답하게 만듭니다. 이것을 **구조화 출력(Structured Output)** 이라고 합니다.

```json
{
  "category": "환불",
  "confidence": 0.92,
  "reason": "상품 불만족 표현"
}
```

이제 프로그램이 쓸 수 있습니다.

```python
if result.category == "환불":
    ...
```

핵심은 **선택지를 미리 좁혀 두는 것**입니다. `category`가 `환불 / 배송 / 기타` 셋 중 하나여야 한다고 스키마에 박아 두면, 모델이 "환불 문의인 것 같습니다"라고 답할 자리가 없어집니다.

```mermaid
graph LR
    A["사용자 문의<br/>(자유로운 자연어)"] --> B["LLM<br/>+ 스키마"]
    B --> C["고정된 구조<br/>{category, confidence}"]
    C --> D["프로그램 분기"]
```

> 구조화 출력을 **랭체인에서 어떻게 쓰는지**는 6.4.4절에서 실습합니다. 여기서는 "왜 필요한가"까지만 잡습니다.

## 판단은 흔들립니다 — 좁혀서 막습니다

LLM은 확률로 고르므로 판단도 흔들립니다. 흔들림을 줄이는 방법은 셋입니다.

| 방법 | 하는 일 |
| :--- | :--- |
| **온도를 낮춘다** | 확률 1등을 그대로 고르게 함 (1.1절) |
| **선택지를 좁힌다** | 자유 서술 대신 정해진 값 중 하나만 고르게 함 |
| **판단 근거를 함께 받는다** | `reason` 필드를 두면 왜 그렇게 골랐는지 추적 가능 |

세 번째가 특히 중요합니다. 에이전트가 이상하게 동작할 때 **모델이 무엇을 보고 그렇게 판단했는지**를 알 수 없으면 고칠 방법이 없습니다.

## 프롬프트는 코드가 아니라 명세입니다

`if` 문을 프롬프트로 옮겼다는 건, **버그가 생기는 자리도 옮겼다**는 뜻입니다.

| | 코드로 짠 분기 | 프롬프트로 넘긴 판단 |
| :--- | :--- | :--- |
| 틀렸을 때 원인 | 조건식이 잘못됨 | 지시가 모호했거나 예시가 없었음 |
| 고치는 법 | 코드 수정 | 프롬프트 수정 |
| 재현성 | 항상 같음 | 같은 입력에도 달라질 수 있음 |
| 검증 | 단위 테스트 | 사례를 모아 비교 |

그래서 프롬프트도 **버전 관리 대상**이고, 바꿨으면 예전 사례로 다시 돌려 봐야 합니다.

## 요약 및 비유

**신입사원에게 업무를 맡기는 상황**과 거의 같습니다.

| 개념 | 신입사원 비유 | 기술적 의미 |
| :--- | :--- | :--- |
| **프롬프트** | 업무 지시서 | 모델에게 주는 자연어 지시 |
| **시스템 프롬프트** | 입사할 때 받은 직무 규정 | 대화 내내 유지되는 규칙 |
| **사용자 메시지** | 오늘 들어온 개별 건 | 매번 바뀌는 입력 |
| **자연어 응답** | 말로 보고함 — 사람마다 형식이 다름 | 파싱 불가능 |
| **구조화 출력** | 정해진 서식에 기입하게 함 | 스키마로 응답 형식 고정 |
| **선택지 좁히기** | 객관식으로 물음 | 열거형으로 값 제한 |
| **판단 근거 요구** | "왜 그렇게 판단했나요" | `reason` 필드로 추적 가능하게 |
| **온도 낮추기** | 튀지 말고 무난하게 | 확률 1등 위주로 선택 |

## 결론

* 조건을 코드로 다 적을 수 없을 때, **판단 자체를 모델에 넘기는 것**이 LLM 기반 의사결정입니다.
* 메시지는 **시스템 / 사용자 / 어시스턴트 역할로 나눕니다.** 사용자 입력을 시스템 프롬프트에 이어 붙이면 지시를 덮어쓸 수 있어 위험합니다.
* 자연어 응답은 형식이 고정되지 않아 **프로그램이 쓸 수 없습니다.** 구조화 출력으로 모양을 강제해야 합니다(6.4.4절).
* 흔들림은 **온도 낮추기 · 선택지 좁히기 · 근거 함께 받기**로 줄입니다.
* 프롬프트는 코드가 아니라 **명세**입니다. 버그가 조건식이 아니라 지시문에서 나므로, 버전 관리하고 사례로 검증합니다.
