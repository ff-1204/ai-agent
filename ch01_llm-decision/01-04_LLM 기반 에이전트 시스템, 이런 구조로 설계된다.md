# 1.4 LLM 기반 에이전트 시스템, 이런 구조로 설계된다

> **공식 문서** — [Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents) · [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

[1.3절](01-03_LLM%EC%9D%B4%20%EB%8B%A4%EC%9D%8C%20%ED%96%89%EB%8F%99%EC%9D%84%20%EA%B2%B0%EC%A0%95%ED%95%98%EB%8B%A4.md)에서 만든 루프는 강력합니다. 무엇을 할지 모델이 알아서 정하니 어떤 요청이 와도 대응할 수 있을 것 같습니다.

그런데 이런 일을 시킨다고 해 봅시다.

> "매일 아침 뉴스 10건을 가져와서 요약하고 슬랙에 올려 줘."

단계가 이미 정해져 있습니다. **가져오기 → 요약하기 → 올리기**. 순서가 바뀔 일도, 중간에 다른 걸 할 일도 없습니다.

이 일을 1.3의 자율 루프에 맡기면 어떻게 될까요? 모델이 매번 "이제 뭘 하지?"를 고민합니다. 어떤 날은 요약을 두 번 하고, 어떤 날은 슬랙 올리기를 빠뜨립니다. **정해진 일을 굳이 매번 판단하게 만든 것**입니다.

에이전트 시스템의 구조는 크게 두 갈래이고, 이 선택이 첫 번째 설계 결정입니다.

## 1.4.1 작업의 단계를 미리 지정한 에이전트 구조

단계와 순서를 **개발자가 코드로 고정**합니다. LLM은 각 단계 안에서만 일합니다. 이런 구조를 **워크플로(Workflow)** 라고 부릅니다.

```mermaid
graph LR
    A["뉴스 수집"] --> B["LLM: 요약"]
    B --> C["LLM: 말투 다듬기"]
    C --> D["슬랙 전송"]
```

여기서 LLM이 하는 일은 **요약**과 **다듬기**뿐입니다. "다음에 뭘 할지"는 묻지 않습니다. 화살표가 이미 코드에 박혀 있으니까요.

**LLM을 안 쓰는 게 아니라, 판단만 안 맡기는 것**입니다. 이 구분이 중요합니다.

| | 워크플로에서 |
| :--- | :--- |
| 흐름 결정 | 개발자 (코드) |
| 각 단계의 내용 | LLM |
| 실행 경로 | 매번 같음 |
| 비용 | 예측 가능 — 호출 횟수가 고정 |
| 디버깅 | 어느 단계에서 틀렸는지 바로 보임 |

> **분기가 있어도 워크플로입니다.** "감성이 부정이면 담당자에게 넘기고 아니면 자동 응답" 같은 조건 분기가 들어가도, **가능한 경로를 개발자가 다 그려 뒀다면** 워크플로입니다. 조건 판단을 LLM이 하더라도 마찬가지입니다.

## 1.4.2 작업의 단계를 동적으로 처리하는 자율 에이전트 구조

이번엔 단계를 안 정합니다. 도구만 쥐여 주고 **다음에 무엇을 할지 매번 모델이 정하게** 합니다. 1.3절의 루프 그대로입니다.

```mermaid
graph TD
    A["요청"] --> B["LLM: 다음 행동 결정"]
    B -->|"검색이 필요"| C["웹 검색"]
    B -->|"계산이 필요"| D["계산기"]
    B -->|"파일을 봐야 함"| E["파일 읽기"]
    C --> B
    D --> B
    E --> B
    B -->|"충분함"| F["최종 답변"]
```

화살표가 **모델의 판단에 따라 그때그때 그려집니다.** 실행 경로가 매번 다릅니다.

이 구조가 필요한 상황은 **미리 그릴 수 없을 때**입니다.

> "이 오류 로그 보고 원인 찾아 줘."

원인이 설정 파일에 있을 수도, 의존성 버전에 있을 수도, 네트워크에 있을 수도 있습니다. **무엇을 봐야 할지는 봐야 알 수 있습니다.** 순서를 미리 못 정합니다.

| | 자율 에이전트에서 |
| :--- | :--- |
| 흐름 결정 | LLM |
| 실행 경로 | 매번 다름 |
| 비용 | 예측 어려움 — 몇 번 돌지 모름 |
| 디버깅 | 어려움 — 왜 그 도구를 골랐는지 추적해야 함 |
| 위험 | 무한 루프, 컨텍스트 초과 (1.3절) |

## 어느 쪽을 고를 것인가

**단계를 그릴 수 있으면 그리세요.** 이게 실무의 기본값입니다.

자율 구조가 더 발전된 형태처럼 보이지만, 실제로는 **통제를 포기하는 대가로 유연성을 사는 것**입니다. 대가가 작지 않습니다.

```mermaid
graph LR
    A["단계를 미리<br/>그릴 수 있나?"] -->|"그릴 수 있다"| B["워크플로"]
    A -->|"봐야 안다"| C["자율 에이전트"]
    B --> D["예측 가능 · 저렴 · 디버깅 쉬움"]
    C --> E["유연 · 비쌈 · 추적 어려움"]
```

| 기준 | 워크플로 | 자율 에이전트 |
| :--- | :--- | :--- |
| 입력의 종류 | 정해져 있음 | 무엇이 올지 모름 |
| 처리 순서 | 미리 알 수 있음 | 해 봐야 앎 |
| 실패 시 영향 | 어느 단계인지 특정됨 | 어디서 어긋났는지 찾아야 함 |
| 운영 비용 | 고정 | 변동 |
| 적합한 예 | 문서 요약 파이프라인, 정기 리포트, 분류 후 라우팅 | 코드 디버깅, 자료 조사, 열린 질문 응답 |

> **둘은 배타적이지 않습니다.** 실제 시스템은 대개 섞습니다. 큰 흐름은 워크플로로 고정하고, 그중 한 단계만 자율 에이전트에 맡기는 식입니다. **11장의 최종 프로젝트**가 정확히 이 모양입니다 — 오케스트레이터가 큰 틀을 잡고, 그 아래 전문 에이전트들이 각자 판단합니다.

이 판단 기준은 **3장에서 싱글 에이전트와 멀티 에이전트를 고를 때 그대로 다시 쓰입니다.** 여기서 확실히 잡고 가세요.

## 요약 및 비유

**패키지 투어와 자유 여행**의 차이와 같습니다. 어느 쪽이 우월한 게 아니라, **일정을 미리 짤 수 있느냐**로 갈립니다.

| 개념 | 여행 비유 | 기술적 의미 |
| :--- | :--- | :--- |
| **워크플로** | 패키지 투어 — 일정표가 있음 | 단계와 순서를 코드로 고정 |
| **자율 에이전트** | 자유 여행 — 그날 정함 | 다음 행동을 LLM이 매번 결정 |
| **워크플로 속 LLM** | 가이드가 현장에서 설명 | 각 단계의 내용은 LLM이 처리 |
| **조건 분기** | 비 오면 실내 코스 (미리 정해 둔 대안) | 경로를 다 그려 뒀으면 여전히 워크플로 |
| **예측 가능성** | 며칠에 얼마 드는지 미리 앎 | 호출 횟수·비용이 고정 |
| **유연성** | 좋은 곳을 만나면 하루 더 머묾 | 예상 못 한 입력에 대응 |
| **무한 루프** | 길을 잃고 같은 골목만 돎 | 종료 판단 실패 (1.3절) |
| **섞어 쓰기** | 큰 일정은 정하고 하루는 자유 | 워크플로 안의 한 단계를 에이전트로 |

## 결론

* 에이전트 시스템의 첫 번째 설계 결정은 **"단계를 미리 그릴 수 있는가"** 입니다.
* **워크플로**는 흐름을 개발자가 고정하고 LLM은 각 단계의 내용만 맡습니다. 예측 가능하고 저렴하며 디버깅이 쉽습니다.
* **자율 에이전트**는 다음 행동을 LLM이 매번 정합니다. 유연한 대신 비용을 예측하기 어렵고 추적이 힘듭니다.
* 조건 분기가 있어도 **경로를 다 그려 뒀다면 워크플로**입니다. 분기 판단을 LLM이 하더라도 그렇습니다.
* 기본값은 워크플로입니다. **자율 구조는 미리 그릴 수 없을 때만** 씁니다. 실제 시스템은 대개 둘을 섞습니다(11장).
* 이 판단 기준은 3장의 싱글 / 멀티 에이전트 선택에서 그대로 다시 쓰입니다.
